The coolest thing about WHIRL is that, by coming up with a clean, general, solution to the name matching problem, WHIRL makes it possible to integrate really substantial amounts of information easily. To demonstrate this, I put together three largish demos, together using dozens of sites. Of course, you can only see a few sample queries from each of these in this "canned" demo. I'll "talk" you through a few queries in a couple of domains, pointing out what I think is interesting.

Computer Games [See accomanying slide]

The game demo shows WHIRL working in a domain that is extremely hard; computer games seem to be named in a very inconsistent manner across different Web sites. To get an idea of the variation, examine this whirl output, which is result of looking for reviews of games named "disney". Consider how difficult it would be to automatically construct keys for these names. How can one determine, for instance, that "Walt Disney World Explorer - Disney Interactive" and "The Walt Disney World Explorer" are the same, but "Disney's Ready to Read with Pooh" and "Disney's Ready for Math with Pooh" are different?

In spite of the messiness of the names, performance on this domain is good, as shown by the two sample queries. The first query is a three-way join that involves matching publisher names from different sources, and also matching game names from different sources. (Hit the "go" button on the form to see the answer.) Interestingly, the game names from one of these sources are not completely extracted from the surrounding text - to make it easier to write the wrapper, I left in a bunch of noise words around each name (e.g., SKU 141137 ----------> $19.95). This doesn't seem to degrade performance much, another benefit using "soft" matching on names. Scroll down to the bottom of the first 40 answers (around ranks 25-35) to see results that depend on soft matching of both publisher names and game names.

Now, a few quick points about the interface you're looking at.

  • The pages you see are stored on disk; in the demo, they're computed on the fly. This usually happens very quickly, as indicated by the runtime near the top of each page. (This is time to compute the query by WHIRL, and ignores time to format the HTML and transfer the data to the browser.)
  • In the real demo, you can page through the answers provided by Whirl, in much the same way you might interact with a search engine like Altavista. It's also possible to click on a column header; this groups the table by the items in that column. You can also "refine" a query by asking that a column match (be similar to) some text you provide.
  • Finally, the items in square brackets indicate the site from which the accompanying text was extracted. In the actual system, you can click on these to take you back to the page that was the "original source" of the text.

Note that the first query is relatively non-selective, so it's easy to find answers using only very good matches of publisher names. The second query in this domain shows why it's important not to just threshold the degree to which names match. Finding any tuples that might answer this highly selective query requires really stretching in matching the publisher names. In particular, it requires using matches that a simple thresholding scheme would probably reject as being unlikely. (If you recall, the match for "Microsoft/Scholastic" and "Microsoft Kids" was ranked behind several incorrect matches.)

Birding [See accomanying slide]

The birding demo shows the same sort of action in a different domain. This domain is somewhat larger; the core of it is (at last count) about 7500 information "resources" of various sorts (pictures, sound files, maps, etc), each indexed by the name of bird species.

Browsing and quick search

The interface for this domain is a bit more developed than for the game demo.

One feature of this demo is browsing. Follow the eyeballs from the order or state links to see how you can drill down into the resource database - either geographically, or by taxonomy. You can do this for all resources, regardless of how the original information was organized; this is done, with a cascaded series of WHIRL queries, ending in a query that does a "soft" match of a bird name (from a state or bird-family listing) against the bird names in the resource list.

The point here is that systems that integrate information can be useful, even without complex user queries. The quick search feature of this demo also illustrates this point. Note that the list of answers for "robin" includes resources tagged only with the scientific name for a robin. This happens because WHIRL uses a big list of complete bird names (i.e., common and scientific names) to expand the user's search string. The query executed "behind the scenes" here is something like:

SELECTbiglist.*,resource.*
FROMbiglist,resource
WHEREsimilar(biglist.name,resource.name) and
similar(biglist.name,"robin")

Handling Free Text

I've also indexed several hundred "birding hotlines"; some examples are shown here (1, 2, 3, 4). These free-text sources were loaded into WHIRL like this: for each hotline, I created a relation containing all the short phrases in the document (where a phrase is a sequence of consecutive words). Browsing the hotlines grounds out in a query that joins the phrases from a hotline with a list of known bird names. As you can see, this works pretty well; so WHIRL is also a neat way of searching for names in a free-text document.

In fact, WHIRL can do much more with free-text. For instance, you could take the table of bird names mentioned in a hotline and, using the standard interface, refine the query to find, say, just phrases about birds in one order. In fact, queries dealing with free text in this way can be arbitrarily complex, as indicated by this sample query.

Note that the query here (roughly, "find pictures of swans geese and ducks") could be posed to a simple word-based IR search engine; but in that case you'd be unlikely to get back pictures labeled "bufflehead" and "oldsquaw".

Experiments [See accomanying slide]

Finally, I've also done some controlled experiments with WHIRL. These were done on simple two-way joins on problems for which I knew the answer - that is, where there is some secondary evidence, other than the names, to tell me if a pairing proposed by WHIRL is correct. Follow the red dots (so, I got tired of eyeballs, ok?) to see how WHIRL fares in matching names for other domains. On each of the WHIRL outputs

  • the first two columns are the names used in the similarity join
  • the last two columns are the keys used to check "correctness" of a pairing
  • the score is rendered in green if the pairing for that row is correct, and red otherwise.
If this is overwhelming, my personal favorites are the park name and restaurant name matches. The performance on joining game names to paragraphs of free text is also pretty striking.

The point of all this is to convince you that WHIRL is robust across domains, and that it's possible to quantify performance for "soft" database systems like WHIRL.
