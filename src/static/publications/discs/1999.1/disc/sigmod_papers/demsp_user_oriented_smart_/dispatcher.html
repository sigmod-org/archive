Overview:
the dispatcher

The Dispatcher is in charge of receiving the user's query and processing it. It generates some information for the View Factory, the Database and the OutputFormatter.

Parsing the query

The query is first sent to an OQL parser that builds an abstract tree representing the query. During the tree construction, the parser tries to match the terms used by the user with terms understood by the system. We can see this task as performing query translation and even sometimes query expansion. If the system is extended to a NL interface, the rule translation will be combined with query translation.

For instance, when expressing query "What are the conferences located in Paris?", the user may write Conf or Confs. Both will be translated into Conference. Moreover, the user may type x.location = "Paris, France" that be translated into x.location.city = "Paris" & x.location.country = "France". The latter is an example of automatic query expansion.

The parser also performs type-checking on path-expressions of the OQL query for both methods and attributes: location.city implies that class Location has a field city.

A component extracts the relevant constants (such as Paris or France) to use them as parameters in the IR query. The choice of relevant IR queries to associate to concept classes, as well as the choice of their parameters is an optimization issue, not yet implemented in AKIRA.

Today, the user's interface is restricted, the extraction capabilities limited and the resulting query language is a subset of OQL. But our approach is promising and has been thought in a more general framework. The idea is based on a volontary total ignorance of the user. He does not want to know how the system is able to build a schema out of his query according to the retrieval and extraction capabilities of the system. The translation from the user's query may then result in a PIQL expression: with general path expressions as opposed to a unique path expression. To answer a query, several different paths along attributes may have to be followed. POQL, such a query language has been defined, studied and implemented at the Verso project in INRIA. The resulting necessary choice among paths raises, again, interesting question of optimization, and dramatically complicates the task of inferring the target structure from the query.

Extracting the target structure

The target structure is the structure inferred from the user's query by matching schema components and completion, required to answer the user's query. For example, when asking "What are the conferences located in Paris?", a target structure composed of two concept classes Conference and Location combined with the attribute location is inferred from the query.

But the target structure is the structure expressed by the user in his query that is understandable by the system to answer the query. Supose that the user is interested by the "conferences where the weather is good (sunny and temperature of 70F)". The only concept class explicitly mentioned in the query is Conference. The system will have to complete in order to define the target structure. Supose that there is a method associated with class Location such as if a date is given as a parameter, then it returns the weather (think of an access to a service such as www.weather.com). Then, the target straucture to answer the query consists of three classes Conference, Date and Location, with attributes submission_deadline, location and weather.

Answering the query

First, the code that represents the filtering criterion, contained in the where clause and is the query sent to the Database (= cache). In a second step, The code that represents the way objects are going to be returned to the user, contained in the select clause, is sent to the Output Formatter. This is similar to the tabular projection for the relational model or the struct(...) construct for the object-oriented model.
